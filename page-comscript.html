ComScript

[UNRESOLVED] The source marks the ComScript name as subject to change and contains unresolved technical placeholders; review them before treating this page as final.

ComScript is a coding language based on Minecraft Commands that eliminates the need for long chains of Command Blocks. ComScript can be natively and directly executed in [see also: lobby] the admin lobby or by typing scripts into the Scripter block.

Errors

Errors due to syntax or any other reason when the script is run are shown in the native terminal located at the bottom of the UI. All errors are red text, warnings as yellow text, and logs as white text.

Error: Undefined data structure(s)

This error appears when undefined variables, arrays, lists, or dictionaries are used.

Error example:

Error: No mandatory execution marker found

This error appears when a selector requiring an execution marker does not have a global marker to fetch from. This can trigger a domino effect of errors since the invalid selectors output null, which may not be compatible with the data type where the selector is used.

Error: Unexpected data type in input

This error occurs when an incompatible data type is used in an input.

Error example:

;

The semicolon is an operator for integers and floats only.

Technical details

Terminology

Relative location selectors

Relative location selectors include any selectors that are location or distance based, meaning that they must have a starting point of execution. These include:

  • @p
  • @n
  • @s
  • @c

If no execution marker is included, then it will error and output null at any use instances.

Native console

The native console is the built-in executor within the esc menu.

Token

A token is any symbol, symbolized, or packaged string that can be used in a value type.

Command selector standardization

All commands with selectors now follow the structure below:

<command namespace> <selector> <action/input> <opt: attributes, booleans, conditions, etc.>

Execution pattern

Selector fetch pattern

If a selector is distance based, such @p (closest player), then the code scans in a spiral pattern in 1x1x1 chunks looking for an entity with the valid conditions for the selector.

Example:

Assume that an entity with the correct conditions is being searched for with a relative location selector. The block Chunks are labeled by scan order. The scan terminates and returns the result after the entity is found.

                 North
          9 10 11 12
          1  2  3  X  13
          8     4
          7  6  5
          X = execution marker location

[see also: Custom execution pattern]

Quotations

Quotations in comscript are unidirectional, meaning that they do not directionally encapsulate text.

Example:

Serif: ""

ComScript: ""

*The two quotes above should look identical but different from Serif, if they don't then your browser may not support unidirectional quotations.

Execution location auto-assumption key

Commands executing without a specified location(specified via the marker keyword)are executed based off of the following rules:

If the script line is encapsulated by a *{} condition statement with a location specifier, then it is executed there.

If no specified location is fetched from the previous condition(s), the execution marker (if one was fetched correctly) becomes the native execution location. If no location is fetched, and a script is executing from a Scripter block, valid selectors execute from the Scripter's location:

  • @p (for locational relative/proportional selectors such as closest player/entity, this is relative to the location of execution) [property P1]
  • @e [see property P1]
  • @s [see property P1]
  • @n [see property P1]

If the script is executed directly from the native console and no location is defined by the previous rules, the script executes globally, causing a syntax error in any relative location selectors.

Scripter block

The Scripter is the block that runs ComScript in game. It is an operator-only block like the command block: it can't be broken in survival and drops nothing. Right-clicking it opens a black code editor (JetBrains Mono font, colour-coded keywords) with the terminal underneath.

  • A redstone pulse runs the script once, one tick after the signal turns on.
  • The Run button saves and runs the script, Stop stops its timers and event blocks, Done saves, and Clear empties the terminal.
  • Running the script again stops the timers and event blocks the last run started.
  • One run (or one tick of a timer, or one event) can run at most 10000 statements, so a script can't freeze the server.
  • Command output appears in the terminal: errors in red, warnings in yellow, everything else in white, each with the time and line number.

Definers in the Scripter

The Scripter accepts local: and global: in front of any statement, but they don't change anything yet because every script is a single file. .get-once and .lock-element aren't supported.

Planned: local: in front of pattern or range will limit it to the block it's in (a class, a run { } or an event block). Without a definer it lasts for the rest of the file. global: will apply it to every file in the header's project.

Definers [unresolved: better name]

local:

The local definer causes any modifier keyword to become a local action. Local actions only perform the modifier within said file or, when encapsulated within a flow-control string, only within that segment unless otherwise stated with global:.

Example:

local:mark add @r.cache-once mobile

global:

.get-once

The .get-once modifier is used on inputs that require a random number generator. .get-once can be used if a event/target entity is randomized, as the .get-once prevents a random number generator from functioning normally.

.lock-element

Custom execution pattern

Custom execution patterns can be defined using the pattern keyword. For a definition and explanation on execution patterns, see Technical details: Execution pattern.

Example:

local:pattern set r-spiral; //sets pattern to spiral

Valid built-in execution patterns:

  • l-spiral: clockwise spiral
  • r-spiral: counterclockwise spiral
  • rand-<radius applier>: randomized
  • top-r-bttmscan: start from top right downwards
  • top-l-bttmscan: start from top left downwards
  • bttm-r-topscan: start from bottom right upwards
  • bttm-l-topscan: start from bottom left upwards
  • odd-checker: first from top left to bottom odd tiles then even tiles
  • even-checker: first from top left to bottom even tiles then odd tiles

Built-in patterns (planned)

Not in the Scripter yet. Without a pattern, selectors use Minecraft's own order (nearest first for @p and @n). The planned version supports these patterns, which differ from the list above:

pattern set spiral; // 1x1x1 cells, clockwise outward from northwest of the marker
pattern set nearest; // closest first
pattern set furthest; // furthest first
pattern set random; // random order

Patterns apply to @p, @n, @e and @a, both in commands and in fetchers. @s is never changed.

Execution marker/location

Execution markers mark where the script would start executing if you would like to override the location of where the scripter block is placed or specify the location of where the script is executed if written in the native console. Selectors that are location-based (nearest entity, etc.)scan in a spiral pattern clockwise starting northwest of the marker to search for valid selectors; see Selector fetch pattern. Execution markers can be defined using the following:

mark add<location (x y z)> <mobility>;

Mobile relative execution markers

Relative execution markers move depending on the base selector and the spacing. These allow scripts to execute depending on the mobile selector; which means that you can have scripts executed at a specific tagged sheep for example. If a script is a macro-script

(meaning executed process takes >2 ticks) then the script execution location stays at the

Syntax:

mark add relative <base selector> <tilde defined relative location>;

Example:

mark add relative @e[type=sheep, tag=cheese] ~~10~;

Setting the marker

  • mark add <x y z>; takes absolute or ~ coordinates. The mobility word (static or mobile) is optional and doesn't change anything for a fixed position.
  • mark add relative <selector> <~ ~ ~>; finds the entity once, at that line. If the offset is left out, it marks the entity's own position.
  • A marker moves every statement after it in the same block. Statements inside run { } and event blocks start from the position the block was given.
  • If the selector matches nothing, the line gives Error: No mandatory execution marker found and the marker stays where it was.
  • store.global set excrd = <x y z>; does the same as mark add <x y z>;.

Charset

Character sets and character operations can be changed manually by using the charset keyword. Charset acts as the <meta> tag in HTML. Charset has the following valid sub- keywords:

Charset store

Charset store changes the current charset.

Example:

charset store UTF-8

Valid charsets for comscript include

  • UTF-8
  • US-ASCII
  • ComScript-EN (default)
  • ComScript-zh-CN (modified in language settings)
  • Comscript-hi-IN (modified in language settings)

For more information, see Charset token (custom substitution).

Charset token (custom substitution)

For convenience reasons, if you would like to create your own token substitution token then you can use the following. The example below a fatal error will occur if you store it as a pre-existing token.

Example:

charset token store &dollar; = &s;;

One token is the abbreviation, and the other closes it.

Using tokens

Every token in the substitution key works in strings and commands, and so does any decimal code like &#36;. They are replaced after $variables are filled in, so &dollar; puts a real $ in a command. The semicolon that closes a token never ends the statement.

Planned, not in the Scripter yet:

  • charset store <charset>; accepts the charsets listed above. US-ASCII makes characters outside ASCII an error; the others keep token substitution on.
  • charset token store &dollar; = &s;; replaces the old token with the new one. Storing a token that already exists is an error.
  • charset store myFormat = {&quot;, $, "pcms", "Ó", "Í"}; creates the custom format described under Custom type.

Inputs in comscript can accept the following formats

  • Unicode — expected formatting: <value>
  • String — expected formatting: <value>
  • Binary (useful for raw files) — expected formatting: <complex value>
  • Boolean — expected formatting: <conditional statement>
  • Float — expected formatting: <value>
  • Integer — expected formatting: <value>
  • Packaged Lists — expected formatting: <complex value>
  • Blockstate — expected formatting: <state>
  • Entity — expected formatting: <name>
  • Item — expected formatting: <item name>
  • Coordinate — expected formatting: <x> <y> <z>
  • Custom format

If you want to change/define the format of a variable or value, you can use the following:

Convert to string

string(<value>);

Convert to entityrange

Entityrange is used for entity iterators.

Only 1-digit binary integers, and strings with boolean names can be converted.

boolean(<value>);

Convert to binary

Anything can be converted into binary, as it is the raw data type.

Example:

Convert to float

Convert to integer

integer(<value>)
int(<value>);

Package a list

Packaging a list allows for mixed values to be combined and still be able to be extracted from a different source.

Syntax:

pack.push(<listname>);

Example:

store set myVar= int(String);

Custom type

Custom types can be stored as a list with all valid strings and/or characters listed within the built-in list.

Example[UTF-8]:

};

The statement above would declare all strings or characters within the parentheses to be the only valid tokens in that data format.

Value types and conversions

Scripter values are integers, floats, strings, booleans, selectors (like @e[type=pig]) and text styles. Integers stay integers until a float is involved.

  • Strings can use "..." or '...'.
  • string()/str() turns any value into text. Floats are rounded to 10 decimal places, so sin(30) shows as 0.5.
  • boolean()/bool()/booleanState() accept only 0, 1, "true" and "false".
  • bin()/createBin() keeps a literal like bin(0101) as written. It turns integers into base 2 and text into the bits of its UTF-8 bytes.
  • integer()/int() drops the decimals of a float, reads a string of 0s and 1s (longer than one digit) as binary, and turns booleans into 1 or 0.
  • float()/flt() reads numbers, numeric strings and booleans.

entityrange(), pack.push() and custom types aren't in the Scripter yet.

Boolean values

In the Scripter, plain true and false values are written <true;> and <false;>. The semicolon inside them doesn't end the statement. Writing a bare true or false is an error.

store new open = <false;>;
store set open = <true;>;

Function block

Function blocks are a new block that creates global functions applicable across all command blocks. When opened, the player assigns a function name and can be assessed with the keyword.

<function name>(<function variables, Booleans, etc.>){
    <function contents>
}

Variables, lists, arrays, and dictionaries created within a function are all stored locally, meaning that you cannot acsess them unless you make them global via

global(<namespace>);

If you would like to turn a global data structure back to local and change all outside instances of the data structure to null, then you can use the following:

local(<namespace>);

Writing functions (planned)

Not in the game yet. The Function block will be a new operator block next to the Scripter, with the same editor plus a name box. One Function block can hold one or more functions:

double(n){
    return($n * 2);
}
void greet(name){
    tellraw @a "Hello $name";
}
  • Every Scripter in the world can call a function, either inside a value (store new x = double(4);) or as its own statement (greet("Steve");).
  • return(<value>); ends a function and gives back its value. A void function uses return(); or just reaches its end.
  • Using a void function's result inside a value is an error, and so is a non-void function that ends without return.
  • Parameters and variables made inside the function are local. global(x); makes x global, and local(x); makes it local again, so return.global x; no longer finds it.
  • A function runs at the position and as the entity of the statement that called it. Its errors appear in the caller's terminal as In double(), line N.
  • Functions are saved with the world, so they keep working when the Function block's chunk isn't loaded.
  • Functions can only be written in a Function block or a header, not in a normal Scripter.

Entity Range Iterators

Entity range iterators are used to iterate over a range of entities that can be defined using the syntax below:

for @client.entityiterator in <entity range selector>{
    <repeat script>
}

Example:


    global(return @getcubeentities(5, 5, 5) as @entities.cube);
    global(return filter.insubtypeof(minecraft:players) as (playerlist{}));
    for @client.entityiterator in entityrange(playerlist{}){
        // script contents
    }

Repeating for each entity

Entity range iterators, @client.entityiterator, @getcubeentities and list filters aren't in the Scripter yet. To repeat a script for each entity, use execute as <selector> run { }, which runs the block once for every entity matched.

Data structure creation

Variables

Creation

Variables are created using store new <varname>=<init_value>;. Multiple variables can be created with the same value using store new <varname>, <varname>=<init_value>;. Global variables (which are built in) can be fetched with return.global<varname>; or return.global <varname> as <varname temp>;.

Formatting

Variables can be created with a preset format (see Input formatting) by using the following:

store set <varname> as <format code>;

Example:

store set cheese as);

Note that variables made with a preset format can still be modified using input formatting syntax.

Modification

Existing variables are modified with the command store set <varname>=<float/int/bool/str_value> Variable values can be manipulated by using alter commands below. Note that once a [see also: Input formatting] variable is created, a modifier command must be used to change the data set type, e.g., float, boolean, string... A space must be used between variables and operator keywords.

Change by -1
store set<varname>++;
Change by 1

And they can also be modified using augmented expressions:

store set<varname>--;
Addition
store set<varname>+<val>;
Subtraction
store set<varname>-<val>;
Multiplication
store set<varname>*<val>;
Division
store set<varname>/<val>;

If you would like to retrieve the remainder of the division statement you can use

store set<varname>/%<val>;

Special operators like sqrt and cosine section.

Variable rules
  • $name anywhere in a command is replaced with the variable's value, for example tp @p $x 64 $z;. Inside values (after =, in if comp, in function brackets) the $ is optional.
  • Variable names start with a letter or _ and contain only letters, digits and _.
  • store new on a name that already exists replaces it with a yellow warning.
  • store set on a name that doesn't exist gives Error: Undefined data structure(s).
  • store set <name> = <value>; must keep the same kind of value: integers and floats mix freely, but storing a string in a number needs a conversion like str(...). store set <name> as <value>; replaces the value and its kind without a conversion.
  • ++ and -- only work on numbers. + on a string joins text.
  • Variables last for the whole run, including the timers and event blocks that run started, so they can keep counting between ticks.
  • return.global isn't in the Scripter yet (see Return values).

Text styles

A Scripter-only addition. A text style is stored like a variable, from the same JSON /tellraw takes, and is put into commands with $name:

store new font(warning) as {"text":"WARNING!","color":"red","bold":true};
tellraw @a $warning;
tellraw @a font($warning, "Run!"); // same style, different text

The JSON is checked when it's stored, and an invalid text component is an error. store set font(<name>) as {...}; changes an existing style.

Execution range

Execution range is a variable that determines the area that the script applies to and executes as. For example, if a script with an execution range of a circle with a radius of 5

foot is outside of the circle, then the script will return null.

Setting the range (planned)

Not in the Scripter yet. The range is measured around the execution marker (or the Scripter if there is no marker):

range set 5; // a sphere with a radius of 5 blocks
range set box 10 5 10; // a 10 x 5 x 10 box centred on the marker
range clear; // no range

Selectors (except @s) then only find entities inside the range. A selector with nothing inside the range finds nothing, so the command or fetcher using it fails. local: and global: work as described under Definers.

Extra math functions

  • squareroot() also works, as well as the spelling above.
  • Powers use ^: 2 ^ 10. Factorials use fact(<val>) or factorial(<val>), for whole numbers from 0 to 20.
  • Angles are in degrees, like Minecraft's rotations. The ^ versions are the inverses (sin^(0.5) is 30) and also give degrees.

Random value

Random inclusive values can be generated in ComScript with the following syntax.

Integer example:

random.randint(<min>, <max>)

Non-inclusive values can be generated using:

random.n.randint(<min>, <max>)

Random floats with a determined fix/round can be generated using:

random.<fix length>.rand(<min>, <max>)

Random value ranges

random.n.randint(1, 6) leaves out the maximum, so it gives 1 to 5. random.2.rand(0, 1) gives a float rounded to 2 decimal places.

Comments

Single-line comments use //. Multiline comments use //[text].

// this is a single-line comment
//[this is a multi
line comment]

Multi-line comments in the Scripter

The Scripter uses the older multi-line form, // "text", which continues until the closing quote. //[text] isn't supported yet and is read as a single-line comment.

// "this is a multi
line comment"

Chain commands

Commands can be chained with a newline:

fill ~~~~3~3~3 Stone
fill ~-3~-3~-3~~~ Stone

They can also be chained with a semicolon:

fill ~~~~3~3~3 Stone; fill ~-3~-3~-3~~~ Stone

Fig 1. MEME

Semicolons between commands

In the Scripter, a newline alone doesn't chain commands: every statement needs its semicolon, even on its own line. Several statements can share a line.

fill ~ ~ ~ ~3 ~3 ~3 stone;
fill ~-3 ~-3 ~-3 ~ ~ ~ stone; say done;

Execute commands

For execute commands, the execute part is erased, and the as, at, in, align, anchored, positioned, rotated, facing, if, unless, run, and store become the command itself. Example:

execute at @p run summon pig
at @p run summon minecraft:pig
Subcommands
As

The "as" subcommand is a sub argument used to execute a script as a certain entity.

Example:

as <entity selector> run {
<script>    
}

The "as" subcommand comes with certain selectors that are given, including:

  • Event/Target Entity: the current entity executed as.
  • Source Entity: the trigger entity, for projectiles and items only.
  • Immediate Source Entity: the immediate trigger entity [for example, the projectile that just impacted a entity selector]
If

The "if" subcommand has a new sub argument: comp. Comp is used to compare values.

if comp <value1> <operator> <value2>
Run subcommand

Instead of running one command, the run subcommand can run a chain, notated by parentheses. It can also run a single command normally.

at @p run (
    // Run a chain of commands
    summon zombie ~~2~
    at @e[type=zombie] run summon lightning_bolt
)
// Run one command
Execute and run blocks
  • Minecraft's execute subcommands need the word execute in front again, because a bare if clashed with ComScript's if comp. A bare Minecraft if or unless is an error that shows the corrected line.
  • if comp and unless comp can be written on their own or mixed with execute subcommands. The operators are == (or =), !=, <, >, <= and >=.
  • A chain after run goes in braces, not parentheses, and each statement inside ends with a semicolon. Using parentheses is an error. A single command after run needs no braces.
  • The block runs once for every entity or position the subcommands reach, in order with the statements around it.
execute at @p run summon pig;
if comp $score >= 10 run say You win;
execute as @a at @s if comp getHealth(@s) < 5 run {
    effect give @s regeneration 5;
    say low health;
}

Event sensing

Scripts executing conditionally during an event or every tick can be started with *{<script>} to execute every tick and *<event namespace>{<script>}.

Example:

*worldEvent.blockBreak{
    at @a run summon minecraft:lightning_bolt;
}

Supported events

The Scripter's event names differ from the example above. It supports:

*blockEvent.blockBreak{ } // a block is broken
*blockEvent.blockPlace{ } // a block is placed
*playerEvent.join{ } // a player joins
*entityEvent.death{ } // an entity dies

An event block runs at the event's position, as the entity that caused it. It can read $event_x, $event_y and $event_z, plus $event_block (for block events) or $event_entity (for join and death).

Timers

*{ } runs every tick. *N{ } skips N ticks between runs, so it runs every N + 1 ticks: *1{ } is every other tick and *19{ } is once a second.

store new seconds = 0;
*19{
    store set seconds ++;
    title @a actionbar "$seconds s";
}

Timers and event blocks keep running until the script is run again, Stop is pressed, or the Scripter is broken or unloaded. The terminal shows what the script is listening for.

List filters filter items from a list based off of a set of conditions and saves the new list locally.

return filter.insubtypeof(<subtype>) as <list (does not need to be declared)>;

return server.fps // current global FPS average

    return @getcubeentities(<extends x>,<extends y>,<extends z>) // list of entities in a cube

Arrays

Dictionaries

return<username>location

Boolean

LoadChunk(x,y,z)? // check if the chunk is loaded
Online(<playername>)? // check if the player is online
Checking chunks and players

LoadChunk() and Online() work in the Scripter. The ? is optional, and Online(Steve) doesn't need quotes. store.global set excrd works as described under Execution marker.

Return values (planned)

Not in the Scripter yet. The variables, lists, arrays and dictionary above will be read with return:

return server.count as online; // stores the value in a variable
return server.fps; // without as, shows the value in the terminal
return Steve "location" as spot; // the dictionary form
return.global score as myScore; // copies a global variable

client.player gives the closest player's name and client.e the closest entity's UUID, so both can go straight into commands. server.fps is the server's ticks per second (at most 20). Coordinates are text in x y z form.

Additional syntax and execution

Header

The header file in a ComScript file is essential for linking all of the projects together. Header files declare execution details globally unless stated otherwise in a file. Header files support the following keywords:

  • mark
  • return
  • void
  • queue
  • provide
  • Global functions
  • Global objects

Setting up a project (planned)

Not in the Scripter yet. Every Scripter will get a name box in its editor, and that name is the file's href. A header is a Scripter whose script starts with header;. The files its queue lists form its project.

header;
mark add 0 64 0; // every file in the project starts here
provide difficulty = 2; // every file starts with this variable
queue add door_logic;
queue add lights;
  • provide <name> = <value>; gives every file in the project that variable when it runs.
  • Functions written in a header can be called by every file in the project, and classes written in a header (global objects) can be called by name.
  • A file can read another project file's variable with $door_logic.count and run its public classes with door_logic.Open;.
  • Running the header itself checks it and shows the project's files in its terminal.

Execution Priority

Execution priority is an integer ranging from 0 to the number of ComScript files in a project that determines when a file should be executed while in queue.

Queue (execution priority)

The queue keyword is a header-file-only keyword used to determine the right-of-way when two files are executed simultaneously. Queue provides an index for each file, ranging from 0 to the number of files in the project, ranking the priority of the files. A lower queue index means higher priority.

Auto queue is a built-in queue configuration that uses the following to determine a file's priority:

  • If a file has runtime keywords that take longer than 1 tick to execute: Priority 1
  • If a file fetches from another source and the opposing file does not need external help: Priority 2
  • If a file is executed first: Priority 3
  • If the file has a name higher in the alphabet when in alphabetical order: Priority 4

If any conditions above are met, return(execute);.

Queue syntax:


store new queueList = {};
private class queue {
    queue add <highest priority file href>;
    queue add <mid priority file href>;
    queue add <low priority file href>;
    return(getqueue) as queueList;
}

Running files in order (planned)

Not in the Scripter yet. queue add <file>; can be written straight in the header, or inside private class queue { } as above, where return(getqueue) as queueList; is allowed but changes nothing.

  • When several project files are started in the same tick, by redstone or the Run button, they run in queue order.
  • Their timers each tick, and their event blocks, follow the same order.
  • queue auto; orders the listed files by the auto-queue rules above: files with timers or event blocks first, then files that fetch from other files or functions, then the order they were started, then alphabetical.

Void functions

If the function being created does not return a value, use this syntax:

void <function name>(<function variables, booleans, etc.>){
    <function contents>
}

Where void functions go (planned)

Not in the Scripter yet. See the planned changes under Function block. Void functions are written in a Function block or a header.

Classes

Classes are an important part of ComScript and object-oriented programming in general. Classes can be named and specified in a header file for script execution modifiers such as execution location and priority. Classes can be created with the following syntax:

public <class name> {
    <class contents>
}

Defining and calling classes (planned)

Not in the Scripter yet. A class is a named section of script. It doesn't run where it's written; it runs each time it's called:

public Door {
    store new opened = 0;
    store set opened ++;
    setblock 10 64 10 air;
}
Door; // runs the class
execute as @p run Door; // calls work after run too
  • A class can be called before or after the line that defines it.
  • A class keeps its own variables between calls, so opened above counts up each time. It can also read and change the file's variables.
  • A mark add inside a class moves that class's marker, which it keeps for its next call. Until then it starts where it was called.
  • private <class name> { } can only be called by its own file, unless another file is allowed with override private. public classes in a project file can be called from other project files with <file>.<class>;.
  • If a class has the same name as a Minecraft command, calling the name runs the class.

Subclasses

Subclasses can be created within a larger scope class to apply a modifier to a specific section within the scope class. Subclasses can be created with the following syntax:

public class <subclass name> extends <scope class> implements <greater scope class (optional)> {
    <subclass contents>
}
How subclasses inherit (planned)

Not in the Scripter yet. A subclass can be written inside its scope class or on its own, and is called by its name like any class. When it runs:

  • It looks up variables in its own variables first, then its scope class's, then the implements class's, then the file's.
  • It starts from its scope class's marker, and its own mark add changes only its own marker.
public Castle {
    mark add 100 70 100;
    store new guards = 4;
    public class Gate extends Castle {
        say $guards guards at the gate; // reads Castle's variable
    }
}
Castle;
Gate;

Grant Private Fetch Access

If you have a private element that you would like to give another file permission to fetch from, use the following syntax to allow localized fetching:

override private(<private object namespace>, <href of file grant permission>, <optional: this file>);

This must be implemented before the line where the other file fetches, and the granting file must have a higher priority value in the header file.

Sharing private classes (planned)

Not in the Scripter yet. The private elements are private classes. override private(Door, lights); lets the project file named lights call this file's private Door class with <this file>.Door;. The third value (this file) is optional and only for readability. Variables in project files can always be read by other project files.
